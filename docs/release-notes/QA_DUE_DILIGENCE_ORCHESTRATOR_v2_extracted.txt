Document Purpose
This document defines a reusable, evidence-driven framework for software assurance, quality engineering,
cybersecurity review, product analysis, and full-spectrum due diligence. It is designed for repository agents, local
engineering agents, audit workers, acquisition teams, procurement teams, investors, boards, insurers, and technical
operators.
The framework deliberately separates:
Assurance: Whether the system is correct, secure, reliable, maintainable, scalable, accessible, deployable,
recoverable, and supportable.
Due diligence: Whether technical, intellectual-property, data, security, commercial, financial, personnel, vendor,
regulatory, insurance, and operational claims are supported by evidence.
Decision support: How verified findings affect release, procurement, investment, acquisition, licensing, closing
conditions, transaction structure, remediation, and integration.
The framework must be adapted to the authorized environment. It must never claim access, execution, testing,
ownership, compliance, certification, valuation, or remediation that did not occur.
Revision 2.0 - Application Assurance Expansion
This revision expands the framework from a repository-centered and web-heavy audit into a multi-surface application
assurance system. It preserves the 22-phase structure while adding controls for mobile, desktop, hybrid, installed,
extension, CLI, embedded, self-hosted, and autonomous-agent software.
The central release principle is:
Source code, a preview URL, a development-server demonstration, an emulator demonstration, or an AI-generated
test suite is not the product users receive. Release assurance must validate the exact signed, packaged, installed,
updated, interrupted, recovered, and distributed artifact.
The expansion addresses common AI-assisted coding failure modes, including invented dependencies, deprecated
APIs, incomplete lifecycle handling, debug configuration shipped to production, tests that reproduce the same
incorrect assumptions as generated code, platform-policy omissions, permission overreach, packaging defects,
hidden native dependencies, unsafe update paths, and source-level checks that never inspect the distributable
artifact.
It also introduces application archetype profiles aligned to the types of systems commonly built in modern product
portfolios:
Cross-platform mobile applications with AI, voice, camera, audio, and sensitive local state
Next.js or React SaaS applications with authentication, multi-tenancy, billing, dashboards, and managed backends
Python and Qt Windows desktop applications packaged as installers or portable executables
IDE extensions and editor forks using webviews, extension hosts, AST transforms, and local tools
Self-hosted AI control planes and autonomous-agent systems operating across local and cloud resources
AI media, prompt, and generation applications with provider cost, content, provenance, and abuse controls
Network-adjacent utilities that require elevated privileges, packet filters, drivers, or reversible traffic controls
CRM, education, wellness, or other data-sensitive systems with role-based workflows and audit obligations
Website discoverability checks remain available, but they are now activated only for public web surfaces. A missing
sitemap or canonical tag is not treated as a native application defect. Conversely, a native application is not
considered ready merely because its embedded website passes SEO checks.

Do not claim access, review, execution, ownership, compliance, certification, valuation, testing, deployment, or

Configuration does not prove operational enforcement.

assessor review.

4. Evidence Governance
4.1 Evidence Classifications
Every material conclusion receives one evidence classification:
VERIFIED_PRIMARY
Confirmed through an authoritative original document, direct system inspection,
repository evidence, executed testing, or authoritative registry.
VERIFIED_CORROBORATED
Confirmed through at least two independent evidence sources.
INDEPENDENT_THIRD_PARTY
Supported by a relevant independent assessment, audit, certification, report,
registry, or confirmation whose scope and currency were verified.
MANAGEMENT_REPRESENTATION
Supported only by a statement from management, an employee, founder, contractor,
system owner, or seller.
SECONDARY_SOURCE
Supported by a non-primary source whose reliability is documented.
INFERENCE
Reasonably inferred from identified evidence but not directly confirmed.
CONFLICTED
Available evidence sources materially disagree.
STALE
Evidence was once relevant but is superseded, expired, or outside the relevant period.

7A.5 AI-Generated Code Assurance Policy
All AI-generated or AI-modified code is untrusted until independently validated.
The fact that generated code compiles, passes a generated test, resembles a common pattern, or came from a well-
known model does not establish correctness, security, compatibility, ownership, or production readiness.
For every generated dependency, API, command, permission, entitlement, configuration key, platform capability,
environment variable, standard, or policy claim:
Verify existence and exact spelling against an authoritative registry or official documentation.
Verify the expected publisher, namespace, repository, license, current maintenance status, integrity data, and
vulnerability state.
Confirm the dependency is necessary and not duplicating an approved dependency.
Build with a lockfile or equivalent resolved dependency record.
Reject packages that appear only in model output or untrusted search results.
Record whether the suggestion was confirmed before installation.
Research presented at USENIX Security 2025 found package hallucinations across all 16 code-generation models
tested, demonstrating that invented package names are a systemic supply-chain risk rather than a rare edge case.
The audit therefore treats package existence as a required verification step, not an optional code-review preference.
High-risk generated changes require designated human review. This includes authentication, authorization,
cryptography, payment, regulated data, database migrations, signing, software updates, permissions, entitlements,
native IPC, WebViews, drivers, packet filters, infrastructure, deployment, deletion, and irreversible actions.

review, or AI-generated test suite cannot independently satisfy these gates.

19. Recommended Execution Note
This framework is intentionally broad. An agent should activate only the phases that apply to the configured mandate
and available evidence. A phase may be NOT_APPLICABLE, PARTIAL, or BLOCKED; it must not be declared complete
without satisfying its exit criteria.
Version-specific standards must be revalidated at execution time. The framework should not hard-code a publication
version as permanently current.
